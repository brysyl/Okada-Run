# Okada Run: 3-lane arcade runner with optional Supabase leaderboard (v2)

Greenfield Vite + React 18 + strict TS game. A pure-TS engine (`src/game-engine`) owns one mutable state object advanced by `update(state, dt)`, a Canvas renderer draws it, and React receives throttled (~10 Hz) HUD snapshots. Audio is procedural Web Audio, and the leaderboard goes to Supabase when env vars are set and to localStorage otherwise. This pass re-checks the v1 findings against commit `25cf51d`. Both blocking v1 issues (false "SAVED", unhandled submit rejection) and the `roundRect` and migration findings are fixed. `tsc --noEmit`, 22 vitest tests and `vite build` all pass when run here. Every feature in the request is present: Danfo/Keke/pothole, Naira/Helmet/Nitro, speed ramp, shake, particles, restart loop, rAF/listener/AudioContext cleanup, and the `.kiro` specs and steering.

Watch for: (1) the public leaderboard remains spoofable by design, now documented in the migration as casual-only (confirmed, non-blocking); (2) a failed remote *read* still falls back to local scores with only a `console.warn`, so the board can show device-local scores as if they were global (confirmed, non-blocking); (3) `useGameLoop`, `useOkadaGame` and `AudioEngine` teardown are still untested (confirmed, non-blocking).

**Verdict**: APPROVED

## High-level view

The write path now reports where a score landed (`'remote'` or `'local'`), and the UI labels device-only saves. The trust model is unchanged: anonymous inserts with client-computed scores, now documented in the migration as casual-only.

The read path is still lenient. A Supabase select error silently substitutes local scores in the same UI, with no indicator.

## Read path still masks remote failure

```
Leaderboard ──> fetchTopScores ──> supabase.select ──ok──> global rows
                                        │ error (console.warn only)
                                        └──> topLocal(localStorage)  (same UI, no label)
```

The write side returns a `SubmitTarget`; the read side has no equivalent. A player who saved remotely and then hits a transient select failure sees a board containing only their own device's scores, with nothing indicating it is not the shared board. It is a cosmetic honesty gap rather than data loss, so it is not blocking.

The anonymous insert policy (`with check (true)`, client-computed score, 10M cap) remains; anyone with the public anon key can post arbitrary scores. Acceptable for a casual board as documented, but the UI should not present it as competitive.
