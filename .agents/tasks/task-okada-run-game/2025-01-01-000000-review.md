# Okada Run: 3-lane arcade runner with optional Supabase leaderboard (v1)

Greenfield Vite + React 18 + strict TS game. A pure-TS engine (`src/game-engine`) owns a single mutable state object advanced by `update(state, dt)`. A Canvas renderer draws it, and React receives only throttled HUD snapshots (~10 Hz). Audio is procedural Web Audio, and the leaderboard goes to Supabase when env vars are set and to localStorage otherwise. `tsc --noEmit`, 19 vitest tests and `vite build` all pass when run locally. Every feature in the request is present: Danfo/Keke/pothole, Naira/Helmet/Nitro, speed ramp, shake, particles, restart loop, rAF/listener/AudioContext cleanup, and the `.kiro` specs and steering.

Watch for: (1) the score-submit path can reject with no handler and always reports "SAVED" even when the Supabase insert failed (confirmed); (2) the Supabase table accepts anonymous inserts of any score up to 10M, so the public leaderboard is trivially spoofable (confirmed); (3) the renderer calls `ctx.roundRect` every frame with no feature check, which throws inside the rAF loop on older browsers (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The engine is cleanly separated from React and the DOM. Per-frame state stays in a ref, the HUD is throttled, and the loop, keyboard, swipe and audio all have teardown paths.

The weak spot is where the game meets storage and the network. The leaderboard fallback hides remote failures from the player, the localStorage write has no error handling, and the database policy trusts the client completely.

Tests cover the pure engine and the local store only; the Supabase-or-fallback decision, hooks, renderer and audio are untested.

<details>
<summary>Issues (6)</summary>

1. **Unhandled submit failure** (confirmed) — `GameOver.submit` has `try/finally` with no `catch`, and `localStorage.setItem` runs outside the `try`. Quota errors or Safari private mode produce an unhandled rejection and no UI feedback. Catch and show an error state.
2. **False "SAVED" on remote failure** (confirmed) — `submitScore` swallows the Supabase `error` and writes locally. The UI then says SAVED and the score never reaches the shared board. Return a result such as `{ where: 'remote' | 'local' }` and surface it, or log the error.
3. **Spoofable leaderboard** (confirmed) — `insert with check (true)` plus a client-computed score allows arbitrary entries up to 10,000,000 and unlimited spam. Document it as casual-only, or move inserts behind an edge function with rate limiting and sanity bounds, for example score against distance.
4. **`roundRect` without guard** (likely) — `renderer.ts` `rr()` calls `ctx.roundRect` for every sprite. Older Safari and Android WebViews lack it, so each frame throws and the game freezes. Add a path-based fallback or a feature check.
5. **Non-idempotent migration** (confirmed) — the table uses `if not exists`, but `create policy` and `alter publication ... add table` fail on re-run. Wrap them in guards or `drop policy if exists`.
6. **Untested fallback and lifecycle code** (confirmed) — add tests for `submitScore`/`fetchTopScores` with a mocked client (error → local), and for `useGameLoop` cancelling rAF on cleanup.

## Leaderboard fallback hides remote failure and local write errors

```
GameOver.submit ──> submitScore ──> supabase.insert ──ok──> return
                                        │ error (discarded)
                                        └──> addLocal ──> localStorage.setItem ──> dispatch event
```

`submitScore` discards the Supabase `error` and quietly stores the score locally. `GameOver` then sets `saved = true` whenever the promise resolves. A player on a flaky connection, or with a misconfigured anon key or RLS, sees SAVED while the shared board never gets the entry, and nothing is logged. `fetchTopScores` has the same silent behavior on read: an error returns local scores that look like the global board.

The opposite failure is unhandled. `addLocal` can throw on quota or private-mode storage, and `GameOver` has only a `finally`, so the promise rejects unhandled and the button just re-enables. The `localStorage.setItem(NAME_KEY, name)` call before the `try` can throw the same way. Neither case reaches the player.

## Anonymous insert policy and client-trusted scores

The migration allows anyone to insert (`with check (true)`). It bounds `score` to 0–10,000,000 and `name` to 12 characters, but nothing ties the score to a real run. Anyone with the public anon key, which ships in the bundle by design, can post a top score directly. This may be acceptable for a casual board, but the board should not be presented as competitive.

The migration is not safely re-runnable: the two `create policy` statements and `alter publication supabase_realtime add table` have no existence guards, unlike the table and index statements above them.

## Canvas `roundRect` dependency in the render loop

`rr()` in `renderer.ts` draws every Danfo, Keke, Naira, Nitro and the player. `CanvasRenderingContext2D.roundRect` is missing in Safari < 16 and some older Android WebViews, and TypeScript's DOM lib does not warn about it. `tick` calls `render` unguarded inside rAF, so an unsupported browser throws every frame. For an arcade game aimed at phones, a small `arcTo`-based fallback is cheap insurance.

## Test coverage

The 16 engine tests and 3 local-store tests cover the game rules well.

Not tested: `submitScore`/`fetchTopScores` branching (Supabase error → local), `subscribeToLeaderboard` cleanup, `useGameLoop` cancelling rAF, `useSwipe`/`useKeyboard` handling, `AudioEngine` teardown, and the `GameOver` flow. The cleanup requirement in the request is therefore implemented but unverified by tests.
